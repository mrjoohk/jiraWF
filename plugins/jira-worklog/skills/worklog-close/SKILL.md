# 마감

로컬 진행 메모 → Jira. **이 워크플로우에서 Jira에 쓰는 유일한 지점이다.**

## 절대 규칙

0. **어느 폴더에 대고 마감하는지 먼저 확정한다.** 폴더는 여러 개일 수 있고 각자 다른 범위를 맡는다. 폴더를 잘못 고르면 그 폴더의 `roots` 번호와 `jira_key` 기록이 어긋나고, 중복 티켓으로 이어진다.
1. **승인 없이 push하지 않는다.** 초안을 보여주고 사용자가 명시적으로 승인한 항목만 올린다.
2. **이미 `jira_key`가 있는 항목은 다시 만들지 않는다.** 중복 티켓은 되돌리기 비용이 크다.
3. **승인 시점에 `state.json`에 항목을 기록하고, push 성공 즉시 그 항목에 `jira_key`를 채운다.** 기록 전에 다음 항목으로 넘어가지 않는다 — 중간에 끊기면 무엇이 올라갔는지 알 수 없게 된다.
4. **완료(Done) 전이는 절대 자동으로 하지 않는다.** 무엇이 끝났는지는 사람만 안다. 이미 끝난 일을 신규 태스크로 만들 때도 만들어만 두고 완료 처리는 사람이 한다.
4-1. **진행 중 전이는 `transition_on_update` 설정을 따른다**(기본 `in_progress`). 손댄 태스크가 아직 "해야 할 일"에 있으면 "진행 중"으로 옮긴다. 근거: 코멘트가 붙었다는 것은 그 일을 하고 있다는 뜻이고, 보드만 보는 팀원에게는 상태가 유일한 신호다. 되돌리기도 한 번의 전이로 끝난다 — 완료 전이와 달리 비용이 낮다.
5. **새로 만든 메인 태스크에는 `"origin": "local"`을 기록한다.** Jira에서 발견한 root와 구별되어야 `INV-3`이 "승인 없이 만들어진 티켓"을 잡을 수 있다.

## 계층 규칙 (Jira 기본 3단을 전부 소진했다)

```
과제(Epic) → 메인 태스크(root, 로컬 R-nnn) → 파생(Sub-task)
```
- **Jira에 티켓이 없는 채로 한 일은 메인 태스크로 새로 만든다.** 부모는 `state.json`의 `epic_key`이고, 타입은 `issue_type_map`의 표준 태스크 타입이다(파생이 아니다). `epic_key`가 `null`이면 부모 없이 만들되 초안에 **"과제 미지정"**으로 표시한다 — 과제별 구획에 안 잡힌다는 뜻이므로 사람이 알고 넘어가야 한다.
- **파생은 전부 Sub-task**로 만든다. 문제(BUG)도 Sub-task다.
- Sub-task는 자식을 가질 수 없다. **파생 작업 중 또 나온 항목은 그 파생 밑이 아니라 메인 태스크 밑으로 평평하게 붙인다.** 계보는 코멘트로만 남긴다.
- 버그 표시 방법은 `state.json`의 `issue_type_map.bug_marker`를 따른다:
  - `label:bug` → 표준 Sub-task로 만들고 레이블 `bug` + 요약 접두사 `[BUG]`
  - `type:<이름>` → 해당 sub-task 계층 커스텀 타입으로 생성

## 절차

### 0. 사전 확인 — Jira에 쓰기 전에 여기서 멈춘다
일일 배치는 읽기만 하므로 잘못 돌아도 다시 돌리면 그만이지만, **마감은 되돌리기 비싼 쪽이다.** 아래 셋 중 하나라도 어긋나면 **중단하고** 사람에게 보고한다.

1. **폴더 확정.** 대상 `WF_HOME`을 확정한다. 불확실하면 사용자에게 묻는다.
2. **스키마.** `.workflow/state.json`의 `schema_version`이 **3**이 아니면 중단하고 `/wf-init` 실행을 안내한다. 구스키마에 대고 마감하면 `roots` 구조가 어긋난 채 티켓이 생성된다.
3. **스코프.** 오늘 집계 파일 `.workflow/agg/{YYMMDD}.json`을 읽어
   - `scope`의 `project_key`·`epic_key`·`title_include`·`title_exclude`가 `state.json`과 **같은지**,
   - `out_of_scope.count`가 **0인지**

   확인한다. 다르거나 0이 아니면 중단하고 일일 배치를 다시 돌리게 한다.

> 왜 여기서 또 보는가: `INV-5`는 `loop_checks.py`가 도는 **일일 배치에서만** 검사된다. 마감은 그 스크립트를 돌리지 않으므로, 잘못 수집된 집계로 마감하면 INV-5가 막으려던 바로 그 사고(같은 태스크에 하위 티켓이 두 번 생성)가 검사 없이 일어난다.

오늘 `daily/{YYMMDD}.md`가 없으면 마감할 원본이 없다는 뜻이므로 중단하고 일일 배치를 먼저 돌리게 한다.

### 1. 메모 파싱
`daily/{YYMMDD}.md`의 `<!-- MEMO:START -->` ~ `<!-- MEMO:END -->` 구획을 읽는다.

**비어 있으면(플레이스홀더만 있으면) 두 갈래다.**

- 사용자가 **이번 대화에서 오늘 한 일을 말했다면**, 그 내용을 메모 구획에 받아쓰고 진행한다.
- 아무 재료도 없으면 그 사실을 알리고 종료한다. 없는 것을 지어내지 않는다.

받아쓸 때 지킬 것:

1. **받아쓰기이지 작문이 아니다.** 사용자가 말한 것만 옮긴다. "그러면 이것도 했겠네" 같은 보충은 금지다. 메모는 이 워크플로우에서 **유일하게 재생성 불가능한 원본**이고, 여기에 들어간 추측은 코멘트·티켓을 거쳐 Jira에 남는다.
2. **적은 내용을 사용자에게 보이고 확인받은 뒤** 2단계로 넘어간다. 메모가 곧 초안의 입력이므로, 여기서 틀리면 뒤의 승인 표는 이미 틀린 것을 예쁘게 보여줄 뿐이다.
3. 표시(`[신규]`·`[파생]`·`[BUG]`)를 붙일지 애매하면 **붙이지 않는다.** 분류는 초안 작성자와 사람이 3단계에서 한다.
4. 기존 메모가 있으면 **덮지 말고 이어 붙인다.**

> 이 경로가 있는 이유: 사람은 대개 파일을 열어 메모를 적기보다 "오늘 이거 했어"라고 말한다. 그 말을 받아 적을 곳이 없으면 그날 기록은 통째로 사라진다. 다만 받아쓰기와 작문의 경계는 사람이 지켜주지 않으므로, 확인 단계(2)를 생략하지 않는다.

인식 규약:
- `- [신규] 내용` → **새 메인 태스크 후보** (Jira에 아직 티켓이 없는 일)
- `- [파생] 내용` → 새 Sub-task 후보
- `- [BUG] 내용` → 새 Sub-task 후보(버그 표시)
- 그 외 줄 → 해당 root의 진행 코멘트 재료

`[파생]`/`[BUG]` 줄이 `[신규]` 줄 바로 뒤에 오면 그 신규 태스크의 자식으로 본다. 다른 root를 명시하면 그쪽을 따른다.

표시가 없더라도 **어느 기존 태스크에도 속하지 않는 일**은 신규 후보로 올린다. 관련 없는 태스크의 코멘트로 밀어 넣으면 그 태스크의 이력이 오염된다. 판단이 서지 않으면 `unclear`로 남긴다.

### 2. 초안 생성 (서브에이전트)
`jira-drafter` 서브에이전트를 생성한다. 전달하는 것은 **메모 원문 + 오늘 집계 파일**뿐이다.
산출물은 `.workflow/draft.json`이며, 형태는 `jira-drafter`의 출력 계약과 **정확히 같다**:
```json
{ "comments":  [ {"local_id":"R-001","jira_key":"XXX-142","body":"..."} ],
  "new_roots": [ {"ref":"N-1","summary":"...","description":"...","done":false} ],
  "children":  [ {"parent_local_id":"R-001","kind":"bug",
                  "summary":"[BUG] ...","description":"..."},
                 {"parent_ref":"N-1","kind":"task",
                  "summary":"...","description":"..."} ],
  "unclear":   [ "분류하지 못한 메모 줄 원문" ] }
```
- **`new_roots`의 `local_id`도 서브에이전트가 만들지 않는다.** 서브에이전트는 초안 안에서만 쓰는 임시 참조 `ref`(`N-1`, `N-2`…)를 붙이고, 메인 세션이 `state.json`의 `roots`에서 다음 `R-nnn`을 이어 붙여 매핑한다. `parent_ref`를 가진 자식은 그 매핑을 따라간다.
- **`children`의 `local_id`는 서브에이전트가 만들지 않는다.** 메인 세션이 `state.json`의 해당 root가 가진 `children`에서 다음 번호(`R-nnn.m`)를 이어 붙인다. **번호는 재사용하지 않는다.** (서브에이전트는 `state.json`을 읽지 않으므로 번호를 알 수 없다. 지어내게 두면 기존 번호와 충돌한다.)
- **`unclear`를 무시하지 않는다.** 3단계에서 별도 구획으로 보여준다.

### 2-0. 본문 문체 검사 (필수)
```
python3 <plugin>/scripts/draft_lint.py --draft .workflow/draft.json
```
- 종료 코드 0 → 지적 없음
- 종료 코드 1 → **중단이 아니라 경고다.** 지적을 3단계 승인 표에 **그대로 함께 보이고**, 사용자가 그대로 승인할 수 있게 한다.

> 문체는 기계가 판정할 수 없다. 대신 **문서로 자랐다는 표시**(머리말·표·길이)와 **팀원이 못 여는 것을 가리키는 표시**(`local_ref` — 로컬 경로·줄번호·지시어)는 셀 수 있다. 앞의 셋이 걸리면 대개 배경 설명이 들어와 있고, 그런 본문은 읽는 사람이 인과를 다시 찾아내야 한다. `local_ref`는 다르다 — 읽는 사람에게 **아무것도 전달하지 않는 문장**이 들어갔다는 뜻이다. 판단은 사람이 하되, 보이지 않는 채로 넘어가지는 않게 한다.
>
> 길이 상한은 설명 300자, 코멘트 600자로 다르다. 설명은 "이 태스크가 무엇인가" 하나만 답하면 되고, 코멘트는 현황 공유라 판단 근거가 되는 수치를 담아야 한다.

### 2-1. 신규 태스크 제목 확정 (필수)
`new_roots`의 각 항목에 대해 반드시 다음을 돌린다. **눈으로 접두사를 붙이지 않는다.**
```
python3 <plugin>/scripts/new_title.py   --state .workflow/state.json --summary "{초안 summary}"
```
- 종료 코드 0 → 출력된 한 줄이 **확정 제목**이다. 이것으로 만든다.
- 종료 코드 2 → 이 폴더가 맡지 못할 제목이다. **만들지 말고 중단**하고 메시지를 그대로 사용자에게 보인다.

> 제목 필터로 폴더를 나눠 쓰는 경우, 접두사 없는 제목으로 만들면 티켓은 Jira에 남는데 이 폴더의 다음 조회에는 **안 잡힌다.** 일지에서 사라지고 `roots`에는 다시 갱신되지 않는 항목이 남는다. 만든 사람이 가장 늦게 알아채는 유실이므로, 만들기 전에 멈춘다. (`title_include`가 있는데 `title_prefix`가 비어 있으면 이 검사는 항상 2를 낸다 — 그것이 옳다. 먼저 `/wf-init`으로 접두사를 정하십시오.)

### 2-1-b. 들어갈 스프린트 확정
`state.json`의 `sprint_mode`를 따른다. 값이 없으면 `active`로 본다.

| 값 | 동작 |
|---|---|
| `active` | 활성 스프린트에 넣는다 (기본) |
| `backlog` | 백로그에 둔다 — 스프린트 필드를 건드리지 않는다 |
| `ask` | 사용자에게 묻는다 |

`active`면 활성 스프린트를 조회한다.
```
project = {KEY} AND sprint in openSprints() ORDER BY updated DESC
```
반환된 이슈의 스프린트 필드(`issue_type_map.sprint_field`, 보통 `customfield_100nn`)는 **지나간 스프린트까지 배열로** 담고 있다. `state == "active"`인 것만 골라낸다.

- 정확히 1개 → 그 `id`를 쓴다
- 0개 → 백로그로 만들되 **활성 스프린트가 없다는 사실을 알린다**
- 2개 이상 → 어느 것인지 **묻는다.** 임의로 고르지 않는다

> 마감이 만드는 태스크는 **이미 하고 있거나 끝난 일**에서 나온다. 백로그로 보내면 "안 할 일" 더미에 진행 중인 일이 섞이고, 스프린트 보드만 보는 팀원에게는 존재하지 않는 일이 된다. 그래서 기본값이 `active`다. 앞으로 할 일을 미리 등록하는 경우에만 `backlog`가 맞다.

`sprint_field`가 `state.json`에 없으면(구 설정) 스프린트 지정을 건너뛰고 그 사실을 알린다 — `/wf-init`을 다시 돌리면 채워진다.

### 2-2. 병합 후보 조회 (`new_roots`나 `unclear`가 있을 때만)
초안이 "신규"로 분류했다고 해서 정말 신규인 것은 아니다. **에픽 안의 기존 태스크에 붙일 일일 수도 있다.** 그런데 오늘 집계 파일에는 이 폴더 범위의 **내 미완료 root**만 들어 있어서, 완료된 태스크나 다른 폴더가 맡은 태스크는 초안 작성자의 시야에 아예 없다. 그래서 여기서 따로 조회한다.

```
project = {KEY} AND parent = "{epic_key}" AND assignee = currentUser() ORDER BY updated DESC
```
`epic_key`가 `null`이면 프로젝트 전체가 되어 목록이 감당 못 하게 커진다. 그때는 `AND updated >= -90d`를 붙이고 **잘랐다는 사실을 알린다.**

응답 원본을 `.workflow/raw/{stamp}_epic.json`으로 저장한 뒤:
```
python3 <plugin>/scripts/merge_targets.py   --state .workflow/state.json --issues .workflow/raw/{stamp}_epic.json
```
범위 안팎·완료 여부를 표시한 번호 매긴 목록이 나온다. **이 목록을 눈대중으로 다시 만들지 않는다** — 3단계에서는 번호만 고른다.

### 3. 승인
초안을 표로 보여준다 — 무엇이 어느 이슈에 붙는지, 새로 생기는 것이 무엇인지. 신규 메인 태스크는 **2-1에서 확정한 제목, 부모 에픽, 2-1-b에서 정한 스프린트**를 함께 보인다. `draft_lint`가 지적한 항목은 그 줄 아래에 **그대로 붙여 보인다.** 사용자가 항목별로 승인/수정/보류할 수 있게 한다. **보류된 항목은 메모에 그대로 남긴다**(다음 마감에 다시 올라온다).

`new_roots`와 `unclear`의 각 항목은 **세 갈래로 고르게 한다.**

| 선택 | 결과 |
|---|---|
| **새 태스크** | 2-1에서 확정한 제목으로 에픽 아래에 만든다 |
| **병합 → 기존 태스크** | 2-2 목록의 번호를 고른다. 그 항목은 신규가 아니라 **그 태스크의 코멘트**가 된다 |
| **보류** | 메모에 그대로 남긴다. 다음 마감에 다시 올라온다 |

병합을 고를 때 두 가지는 **고르기 전에 다시 알린다.**
- 대상이 목록에서 `밖`이면 이 폴더가 맡지 않는 태스크다. 코멘트는 남지만 이 폴더의 일지에는 나타나지 않는다.
- 대상이 완료 상태면 다음 일일 배치의 미완료 조회에 안 잡힌다.

**병합 대상이 `state.json`의 `roots`에 없으면 그 아래에 파생을 만들지 않는다.** 파생 번호(`R-nnn.m`)를 매길 자리가 없고, `render_daily.py`가 "오늘 할 일"에 찍을 근거도 없다. 그런 자식은 **보류로 돌리고** 그 사실을 알린다. 코멘트만 남기는 것은 문제없다.

`unclear`는 **별도 구획으로 원문 그대로** 보여주고 사람이 분류하게 한다. 사람이 분류하지 않으면 그 줄은 메모에 그대로 남긴다 — 조용히 버리지 않는다. 서브에이전트가 판단을 못 한 줄이 아무 데도 안 남으면, 그날 적어둔 것이 사라졌다는 사실조차 남지 않는다.

### 3-1. 전이 대상 확인
`state.json`의 `transition_on_update`가 `in_progress`(기본)이면, **이번에 손대는 태스크 중 아직 시작 전인 것**을 추린다.

대상: 코멘트를 받는 root, 그리고 이번에 새로 만드는 태스크.
조건: 현재 `status.statusCategory.key`가 `new`인 것만. `indeterminate`는 이미 진행 중이고, `done`은 **건드리지 않는다** — 끝난 일에 코멘트를 다는 것과 그것을 다시 여는 것은 다른 판단이다.

전이 ID는 프로젝트마다 다르므로 `getTransitionsForJiraIssue`로 조회해 **`to.statusCategory.key == "indeterminate"`인 것**을 고른다. 이름(`진행 중`·`In Progress`)으로 찾지 않는다 — 언어와 워크플로우에 따라 다르다.

- 정확히 1개 → 그것을 쓴다
- 0개 → 전이하지 않고 그 사실을 알린다
- 2개 이상 → **묻는다.** 임의로 고르지 않는다

승인 표에 `해야 할 일 → 진행 중`으로 함께 보인다. 항목별로 뺄 수 있다.

`transition_on_update`가 `none`이면 이 단계를 통째로 건너뛴다.

### 4. 반영 (MCP)
승인된 것만, **이 순서대로**. 신규 메인 태스크가 먼저다 — 그 키가 있어야 자식을 붙일 수 있다.

0-a. **병합으로 바뀐 항목.** 신규가 아니므로 만들지 않는다. 2단계 초안의 `comments`에 대상 `jira_key`로 옮겨 붙이고, 그 항목의 `ref`를 가리키던 자식은 대상 root의 자식으로 다시 건다(대상이 `roots`에 없으면 3단계에서 이미 보류됐다).

0-b. **신규 메인 태스크.** 승인 즉시 `state.json`의 `roots`에 다음 `R-nnn`으로 append한다:
   ```json
   {"jira_key":null,"epic":"<epic_key>","origin":"local",
    "summary":"<확정 제목>","approved_at":"<ISO8601>",
    "first_seen":"<YYYY-MM-DD>","last_seen":"<YYYY-MM-DD>","children":[]}
   ```
   그다음 Jira에 생성한다 — 부모 = `epic_key`, 타입 = 표준 태스크, **스프린트 = 2-1-b에서 정한 id**(`{sprint_field}: <id>`). 반환된 키를 **즉시** 그 레코드의 `jira_key`에 채운다. `ref` → `R-nnn` → Jira 키 매핑을 들고 있다가 자식에게 물려준다.
1. **승인 즉시 `state.json`에 기록한다.** 새 파생은 `roots[{parent_local_id}].children`에 아래 형태로 append한다:
   ```json
   {"local_id":"R-001.3","kind":"bug","summary":"[BUG] ...",
    "approved_at":"<ISO8601>","jira_key":null}
   ```
   **필드를 줄이지 않는다.** `local_id`·`kind`·`summary`는 다음 일일 배치의 `render_daily.py`가 "오늘 할 일"에 파생을 찍을 때 그대로 읽는 값이고, 빠지면 **다음 날 배치가 죽는다.**
2. 코멘트 추가
3. Sub-task 생성 → 반환된 키를 **즉시** 같은 레코드의 `jira_key`에 채운다
4. 파생을 만들었으면 **메인 태스크에 그 사실을 코멘트로 남긴다**(보조 기록 — 없어도 `parent`로 추적되지만 일지 가독성에 쓰인다)
5. **진행 중 전이** — 3-1에서 추리고 승인된 것만. 코멘트·티켓이 먼저이고 전이가 마지막이다. 전이가 실패해도 기록은 이미 올라가 있어야 한다(그 반대는 상태만 바뀌고 내용이 없는 상태를 남긴다). 실패한 전이는 다음 마감이 재시도한다 — 조건이 `statusCategory == new`이므로 여러 번 돌아도 안전하다.

신규 메인 태스크도 같다 — `approved_at`은 있고 `jira_key`가 `null`이면 아직 안 만들어진 것이고, 다음 마감이 재시도한다. 다만 그 항목은 Jira에 없으므로 다음 일일 배치의 조회 결과에는 안 나온다. 재시도 전까지는 `roots`에만 남는다.

> 승인과 생성 사이에 끊기면 그 항목은 `jira_key`가 `null`인 채 남는다. 그것이 의도된 복구 상태다 — 다음 일일 배치가 "미등록 파생 n건"으로 표시하고(`aggregate.py`의 `children_pending`), 다음 마감이 재시도한다. `approved_at`은 있고 `jira_key`가 없는 것은 위반이 아니다. `INV-3`이 잡는 것은 그 **반대**(`jira_key`는 있는데 `approved_at`이 없다 = 승인 기록 없는 push)다.

### 5. 마무리
- 처리된 메모 줄에 `✓ {jira_key}`를 덧붙인다(삭제하지 않는다 — 그날의 원본 기록이다).
- `logs/{stamp}/evidence.json`에 최소 다음을 남긴다: `{"tool":"worklog-close","timestamp":...,"daily":...,"scope":{...},"comments_ok":n,"new_roots_ok":n,"merged_ok":n,"children_ok":n,"transitioned":[...],"failed":[...],"keys_created":[...],"unclear_left":n}`. 나중에 문서가 인용할 수 있는 것은 이 파일뿐이다 — 콘솔 출력만 남기면 인용할 것이 없다.
- 실패한 항목은 **초안에 그대로 두고** 다음 실행에서 재시도 가능하게 한다.
